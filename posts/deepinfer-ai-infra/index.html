DeepInfer开源之后：AI Infra正在从算力竞争走向数据搬运与状态池化

从 Shared-Nothing、存算分离到 KV Cache Pooling，重新理解下一代 AI 推理基础设施

JamePeng

原载于 澄鸿AI踢桃

从 Shared-Nothing、存算分离到 KV Cache Pooling，重新理解下一代 AI 推理基础设施

最近，DeepSeek 开源了其大规模推理框架 DeepInfer。 相比于模型参数、推理速度和 Benchmark，我更关注这次开源背后所揭示的 AI Infra 架构变化。

从早期的 Shared-Nothing，到云时代的存算分离、存储池化，再到如今的 Prefill/Decode 分离与 KV Cache Pooling，分布式系统正在经历一轮新的资源解耦。

与此同时，网络技术也在持续发展：从传统 TCP/IP 数据传输，到 RDMA、GPUDirect，再到 400G、800G 乃至 1.6T 光互联。

这些变化最终指向同一个问题：

当 GPU 算力增长越来越快，如何以更低成本，让计算单元及时获得所需要的数据与状态？ 我认为，这是理解下一阶段 AI Infra 发展的一个重要切入点。

01｜从 Shared-Nothing 到 KV Cache Pooling

早期分布式系统普遍采用 Shared-Nothing 架构：每个节点拥有独立的计算、内存和存储资源。 这种架构具有良好的水平扩展能力，但也存在一个长期问题：计算与数据位置紧密绑定，容易产生资源利用不均衡。

随着云计算发展，存算分离逐渐成为主流架构之一。 计算节点负责执行任务，存储池负责保存数据。两者可以独立扩缩容，通过网络实现共享访问。

如今，类似的变化正在 LLM 推理系统中出现。 传统推理部署往往将模型计算、Prefill、Decode 和 KV Cache 绑定在同一个 GPU 工作组中。

但长上下文与多轮 Agent 任务正在改变这一模式。 一个 Agent 可能拥有数万个 Token 的历史上下文，而新一轮工具调用只增加几百个 Token。

如果每次都重新计算历史上下文，显然非常浪费。 于是，KV Cache 开始从 GPU 内部的临时缓存，演变为可以跨请求、跨计算节点共享的集群级资源。

这就是 KV Cache Pooling 的价值。

02｜DeepInfer：模型计算与状态管理开始深度协同

DeepInfer 是 DeepSeek 面向其模型构建的高性能推理框架。

从公开源码可以看到，它不仅涉及 FlashMLA、DeepGEMM、DeepEP 等高性能算子，还包含异步调度、KV Cache 管理、SWA Bounded Replay 等机制。

DeepSeek 生产推理系统采用更完整的架构：

  • Vision Encoder：负责视觉编码。

  • Prefill：负责输入上下文处理。

  • Decode：负责持续生成 Token。

  • KV Cache Storage：负责跨请求的上下文状态复用。

值得注意的是，DeepSeek 没有简单地将所有 KV Cache 放入远程 SSD。

它采用了分层状态管理：

存储层
主要承担的任务
GPU HBM
当前推理所需的热 KV 状态
Host DRAM
SWA 状态、临时 KV 缓冲
3FS SSD Pool
可跨请求复用的持久化 Block KV

通过 3FS 分布式存储，Prefill 节点不再必须绑定某个特定的缓存位置。 这降低了 Prefix Affinity 与计算负载均衡之间的冲突，使 GPU 调度获得更大的灵活性。

更有意思的是，DeepSeek-V4.1-Flash 将全局 KV Cache 压缩至约 890 Bytes/Token，并通过 SWA Bounded Replay 进一步降低需要长期保存的状态规模。

这说明模型层面的 KV 压缩，已经不只是显存优化，而是在直接改变存储和网络的成本结构。 需要说明的是，DeepInfer 当前开源的主要是推理引擎；完整的生产级 KV 存储服务及跨副本负载均衡组件尚未全部开源。

03｜一个容易忽略的瓶颈：KV Cache 搬运比计算更麻烦

在 Agent 场景里，随着 Prefix Cache 命中率提高，GPU 可以避免大量重复 Prefill。 但缓存命中不代表数据已经在 GPU HBM 里。

相反，系统可能需要从 SSD 读取大量历史 KV，再通过网络与 PCIe 搬运到 GPU。 这就产生了新的瓶颈：Data Movement。

举个例子，假设某种 KV 布局下，每个 Layer Block 为 22,784 Bytes，64K Tokens 对应 512 个 Block。

单层需要搬运约 11.13 MiB。 看起来数据量不大，但这些 Block 的源地址和目标地址可能都是离散的。

如果通过 cudaMemcpyAsync 逐块复制，就意味着数百次独立操作提交。

在 DualPath 论文的测试环境中，单次 CUDA Copy 提交开销约为 5–7 微秒，而 RDMA Work Request 提交约为 1 微秒。

因此，问题不只是传输了多少字节，还包括为了传输这些字节，需要付出多少次操作提交与同步成本。

主要存在四种实现思路：

方案
特点
主要局限
CUDA Copy Engine
不直接占用 SM
细粒度提交开销
CUDA Batch Copy
批量降低 API 调用次数
仍需处理批量描述和资源竞争
SM Gather
灵活处理离散地址

GPUDirect RDMA
NIC 直接参与 DMA

DeepSeek 选择 GDR 的重要原因之一，就是让网卡承担细粒度 KV 搬运，并避免每个 Block 都需要 CUDA Copy API 提交。

但还有一个更深层的原因：NIC 能同时承担数据传输和硬件流量调度。 它可以让模型计算通信保持高优先级，而 KV 换入利用空闲带宽，降低对前向计算的干扰。

04｜DualPath：真正的创新不只是升级网速

2026 年，DeepSeek 等研究团队提出了 DualPath，针对 Agent 推理中的 KV Cache 存储带宽瓶颈进行优化。

在传统 P/D 分离系统中，历史 KV 通常由 Prefill 节点从远程存储读取。

这可能导致：

Prefill 节点的 Storage NIC 已经满载，而 Decode 节点的 Storage NIC 却仍然空闲。 DualPath 提供了第二条数据路径。

除了让 Prefill 直接从存储读取 KV，还允许 Decode 节点先利用自己的 Storage NIC 读取历史 KV，再通过高速计算网的 RDMA 通道转交给 Prefill。

Prefill 计算完成后，新产生的 KV 再与原有状态汇合，供 Decode 使用。 这样，系统就能同时利用 P/D 两侧的存储网络带宽。

DualPath 论文报告，在其测试负载中，离线推理吞吐最高提升约 1.87 倍，在线服务吞吐平均提升约 1.96 倍，同时满足所测服务延迟约束。

这组结果让我意识到：

比单纯提高网络带宽更重要的，可能是让原本闲置的网络资源真正参与工作。

05｜从 400G 到 1.6T，网络升级也存在收益边界

AI 数据中心网络正在经历 400G、800G、1.6T 的迭代。 但光模块的标称速率不等于 GPU 实际可获得的数据传输速度。

链路
理论单向带宽
400G
50 GB/s
800G
100 GB/s
1.6T
200 GB/s

数据从存储系统进入 GPU，至少可能经过 Storage NIC、网络交换机、Host DRAM、PCIe 与 GPU HBM。 整体有效吞吐由最慢的一环决定。

例如，PCIe 5.0 x16 的理论单向带宽约为 63 GB/s。 即使使用 800G 网络，如果数据必须完整经过同一条 PCIe 5.0 x16 链路，实际吞吐也不可能达到 100 GB/s。

同样，如果 SSD 后端只能持续提供 40 GB/s，升级 1.6T 光模块也无法直接解决问题。 因此，下一阶段 AI Infra 的建设不能只看光模块、GPU 和交换机的单项参数。

真正重要的是 Storage Fabric、Compute Fabric、PCIe、Host Memory 与 GPU HBM 的端到端匹配。

400G 到 1.6T 的技术进步当然重要，但它必须与更好的拓扑规划、数据压缩、传输调度和缓存复用结合，才能转化为有效吞吐。

400G 到 1.6T：网络速度不等于有效吞吐

06｜我的判断：AI Infra 正在进入 Compute-State Co-Design 阶段

从 DeepInfer 和 DualPath 可以观察到，AI 推理基础设施的优化已经不再局限于单个 GPU 或单个算子。

过去，我们主要关注：

  • GPU FLOPS 有多高。

  • HBM 带宽有多大。

  • 模型能够跑多少 Tokens/s。

现在，还必须关注：

  • 哪些 KV 状态值得保存？

  • 哪些可以低成本重计算？

  • 历史 KV 应该保存在 HBM、DRAM 还是 SSD？

  • 从哪个计算节点读取缓存最合适？

  • 哪条网络路径当前最空闲？

  • 如何避免 KV 传输影响 MoE 专家通信？

  • 网络升级与 KV 压缩，哪个能带来更高的成本收益？

我认为，未来的推理系统会逐渐从单纯的 Compute-Centric，转向更强调 State-Aware Scheduling 的架构。

换句话说，系统不再简单地把请求交给一组 GPU 执行，而是综合考虑计算、状态位置、网络、存储以及重计算成本，选择更合适的执行路径。 这也与未来长时间运行的 Agent 体系有关。

Agent 需要的不只是更大的 Context Window，还需要更便宜的上下文恢复、更可控的状态生命周期，以及能够跨计算实例复用的执行资源。

进一步来看，如果 Recurrent State、KV Cache 和长期记忆能够采用不同的持久化与恢复策略，未来甚至可能形成一种更加灵活的 Compute-State Disaggregation 架构。

当然，这还是一个需要持续验证的研究方向，并非 DeepInfer 已经完整实现的能力。

写在最后

回顾 Shared-Nothing、存算分离、存储池化，再到今天的 KV Cache Pooling，我认为这条技术演进线索非常清晰：

计算资源正在不断摆脱对数据物理位置的依赖

而数据与中间状态也正在获得更灵活的生命周期管理方式。 DeepInfer 的价值，不只是它让 DeepSeek 模型推理更快。 它让我们看到，模型架构、KV 压缩、分布式存储、RDMA、PCIe 和全局调度，正在共同决定下一代 AI 服务的实际运行成本。

未来 AI Infra 的竞争，依然离不开算力。 但决定算力能否被充分利用的，越来越可能是那些隐藏在 GPU 之间的数据流动、缓存状态和调度机制。

更强的 GPU 决定计算能力的上限

而更好的状态管理与数据移动架构

决定有多少算力真正转化为有效的智能服务。 这或许才是 DeepInfer 带给我们的重要启示。

GPU 决定了计算能力的上限，而状态管理、数据流动与全局调度，正在决定这些算力能够以多低的成本转化为真正有效的智能服务。
